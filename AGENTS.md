# Calendar Sidebar

Always-on-top Windows desktop sidebar showing today's events from a
**Radicale / CalDAV** server. PyQt6 hosts a WebEngine that renders a
Svelte/SvelteKit frontend; a FastAPI/uvicorn backend runs on a background thread
and serves event CRUD over CalDAV. A system tray icon provides show/hide and quit.

## Architecture

```
widget.py    PyQt6 window, tray icon + server thread launcher
server.py    Composition root: reads env, builds the provider, creates the app/server
backend/     Provider-agnostic backend (imports never touch os.environ)
  models.py    CalendarEvent domain model
  provider.py  CalendarProvider interface + error taxonomy
  radicale.py  RadicaleProvider: CalDAV reads/writes over one server
  registry.py  ProviderRegistry: lookup + cross-provider aggregation
  app.py       FastAPI app factory (dependency-injected registry)
src/         Svelte/SvelteKit frontend (adapter-static)
build/       Compiled frontend — generated by bun run build (gitignored)
run.vbs      Silent Windows launcher (hides the console)
log/         Runtime log files: widget.log, server.log (gitignored) — the only output when run via VBS
.env         Radicale URL + credentials (gitignored)
```

### Dependency injection

`server.py` is the only module that knows which concrete provider exists. It
builds a `ProviderRegistry` holding `RadicaleProvider(RadicaleSettings(...))`
and passes it to `backend.app.create_app(registry)`. Routes declare their
dependency via `RegistryDep` (`Depends(get_registry)`); the provider itself
receives its configuration by constructor injection and never reads the
environment. Adding another provider means writing one `CalendarProvider`
implementation and one line in `build_registry` — no route changes.

## Running

```
bun install          # install frontend deps (once)
bun run build        # compile Svelte frontend (required once)
uv run widget.py     # start the app (uv handles all Python deps)
```

Or double-click `run.vbs` for a silent, no-console launch. All log output goes to `log/`.

`bun run check` runs `svelte-check` for frontend type errors.

The Radicale server is a separate program and must already be running — see
**Radicale setup** below.

## Ports

The API server binds 8764 by default and scans upward for a free port if it's
taken. Nothing external points at it (the widget and the embedded UI both use
whatever port the server reported), so a fallback is harmless.

## Local API hardening

The API is bound to `127.0.0.1` and is only meant to be reached by the bundled
WebEngine view. Do not loosen any of the following:

- `TrustedHostMiddleware` allows only `127.0.0.1` and `localhost`, so a DNS-rebinding page cannot reach the API.
- `/docs`, `/redoc`, and `/openapi.json` are disabled.
- The SPA catch-all resolves each request path and rejects anything that escapes `build/` (e.g. `/%2e%2e%2f.env`).
- Radicale credentials live in `.env` (gitignored) and are only ever sent to the configured CalDAV URL, over whatever transport that URL names.
- WebEngine feature permissions (camera, clipboard, geolocation…) are denied outright — the UI needs none of them.

A named-mutex guard prevents a second instance from starting.

## Python deps

Declared in `pyproject.toml`; `uv run` installs them automatically into the project environment. No inline `# /// script` headers, no pip.

CalDAV is done with `python-caldav` (`caldav`) + `icalendar`; `tzlocal` resolves
the machine's IANA zone. Nothing here talks HTTP to CalDAV by hand.

## Frontend deps

Bun only — `bun.lock` is the lockfile. Do not add `package-lock.json` or `pnpm-workspace.yaml`.

## Radicale setup

1. Serve the collection over HTTP(S) — this project's instance runs Radicale on
   `127.0.0.1:5232` with htpasswd auth (`C:\radicale\config`, users in
   `C:\radicale\users`, data in `C:\radicale\collections`).
2. Copy `.env.example` to `.env` and set:

   ```
   RADICALE_URL=http://127.0.0.1:5232
   RADICALE_USERNAME=me
   RADICALE_PASSWORD=...
   ```

   `RADICALE_URL` may be the server root or a principal URL
   (`http://127.0.0.1:5232/me/`); python-caldav discovers the rest. Missing URL
   or username is not fatal — the sidebar reports "No calendar configured" and
   names the variables to set.
3. Optionally set `RADICALE_CALENDAR_IDS` to a comma-separated list of calendar
   ids, display names, or URLs. Unset means "every calendar that accepts
   events"; the first entry is also where new events are created.

## Calendars

`GET /api/events` merges today's events from **every calendar** on the server,
tagging each with `provider` (`radicale`), `calendarId`, and the calendar's own
colour (`calendar-color`); the text colour is derived from it for contrast. One
calendar failing does not blank the sidebar: failures are logged and the other
calendars' events are returned; the request only errors when every calendar
fails. All-day events are still returned (they count for the empty state) but
the frontend filters them out of the grid, so they are read-only in this UI.

`PATCH`/`DELETE /api/events/{id}` accept `?provider=` and `?calendar_id=` so an
event is edited through the calendar it came from, plus `?original_start=` to
target a single occurrence of a recurring event. `POST /api/events` takes an
optional `provider` field (defaults to the first configured provider).

Recurring events are stored as one master `VEVENT` plus one override per changed
occurrence, so the sidebar edits the occurrence the user touched rather than the
series: a move/resize/rename writes a `RECURRENCE-ID` override (replacing any
existing one for that occurrence), and removing an event adds an `EXDATE` to the
master instead of deleting the series. The UI sends the occurrence's original
start back as `originalStart`/`original_start`; without it, a series-level edit
is performed.

## CalDAV gotchas (learned the hard way)

- **Every written time carries a real IANA `TZID`** (`tzlocal`), never a bare
  offset. `datetime.now().astimezone()` on Windows yields a *Windows* zone name
  (`India Standard Time`), and `icalendar` will happily serialize an offset as
  `TZID="+05:30"`; Radicale rejects both ("VTIMEZONE components must contain a
  valid TZID") and other clients can't resolve them. All writes go through
  `_localize()`.
- **Never call `Calendar.event_by_uid()` / `get_object_by_uid()` / an untyped
  `search()`** against Radicale here: with no time range those paths expand
  recurrences from `datetime.min`, which has no local-time representation on
  Windows, and `OSError: [Errno 22]` escapes from the library. The provider
  looks events up with `search(uid=..., post_filter=False, comp_class=Event)`
  and applies the exact-UID match itself.
- **`save(only_this_recurrence=True)`** (python-caldav's built-in "merge an
  override into its master") hits the same date-less lookup and crashes, so the
  provider appends the override component itself inside
  `edit_icalendar_instance()` and saves the resource.
- A resource is only ever written after `resource.save()`, which sends the
  ETag it was read with — a concurrent change surfaces as a `PutError` instead
  of a silent overwrite.

## Debugging

When launched via `uv run widget.py` or `run.vbs`, uvicorn runs inside the widget process, so **all** output — API and CalDAV messages included — lands in `log/widget.log`. `log/server.log` only appears when you run `uv run server.py` standalone.

Key log lines to look for:

| Log message | What it means |
|---|---|
| `No calendar provider configured` | `.env` has no `RADICALE_USERNAME` |
| `Radicale: configured` / `not configured` | Startup summary of the provider |
| `API request rejected — no calendar provider is configured` | 401 on event fetch; set the `RADICALE_*` variables and restart |
| `Radicale rejected the configured credentials` | 401 from the server — wrong `RADICALE_USERNAME`/`RADICALE_PASSWORD` |
| `Cannot reach Radicale at ...` | Server down, wrong port, or wrong URL |
| `Radicale request failed for every calendar` | Every calendar errored; the log has the per-calendar tracebacks |
| `Radicale fetch failed for calendar ...` | One calendar errored; the rest still render |
| `Could not read properties of ...` | Calendar metadata (name/colour) unavailable — falls back to defaults |
| `Skipping malformed event in ...` | An event had no usable `DTSTART`; the rest still render |
| `Radicale event ... occurrence ... removed` | A single occurrence was excluded with `EXDATE` (series kept) |
| `Radicale has no calendar that accepts events` | No `VEVENT` calendar visible to this account |
| `Unknown calendar ... on Radicale` | `calendar_id` in the request matches nothing (stale UI state) |
| `Event ... was not found on Radicale` | The event was deleted elsewhere; reload the sidebar |
| `API server not ready yet — retrying` | Widget waits for the port to bind before loading the UI |
| `Retrying UI load in ... ms` / `WebEngine failed to load ... (attempt n/5)` | Page load failed; the widget retries with backoff |
| `Giving up on UI load` | Five consecutive load failures — restart the app |
| `Another Calendar Sidebar instance is already running` | Single-instance guard tripped |

Radicale's own log (`C:\radicale\radicale.log`) is where a rejected `PUT`
explains itself; `Bad PUT request ... (prepare)` is the usual place to look.

## Conventions

- Python: `uv` only (no pip), f-strings, full type hints, loguru for all logging.
- No `import *`.
- Keep `widget.py` focused on the Qt layer; keep business logic in the `backend/` package. `server.py` is the composition root — env parsing and provider wiring only.
- `backend/` modules must not read `os.environ`; configuration is injected from `server.py`.
- New providers implement `CalendarProvider` and are registered in `build_registry`.
- Shutdown path: Qt quit → `CalendarWindow.shutdown()` sets uvicorn's `should_exit` for a graceful stop.
